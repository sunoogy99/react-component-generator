# Commit

변경사항을 분석해 컨벤션에 맞는 커밋을 만든다. 별도의 승인 절차 없이 바로 커밋한다.

## 절차

### 1. 변경사항 분석

다음을 실행해 현재 상태를 파악한다.

- `git status`: 변경·추가·삭제된 파일과 untracked 파일 확인
- `git diff`: 아직 stage하지 않은 변경 확인
- `git diff --staged`: 이미 stage된 변경 확인
- `git log --oneline -10`: 이 저장소의 기존 메시지 스타일 확인

변경이 없으면 "커밋할 변경사항이 없습니다."라고 알리고 종료한다.
Git 저장소가 아니면 그 사실을 알리고 `git init` 여부를 사용자에게 묻는다.

### 2. 논리적 단위로 분류

- 한 커밋은 하나의 목적만 담는다. 서로 다른 목적의 변경(예: 기능 추가와 설정 변경)은 나눈다.
- 같은 목적의 파일(컴포넌트, 스타일, 테스트)은 한 커밋으로 묶는다.
- 파일 하나 안에 목적이 섞여 있으면 사용자에게 알리고 나눌지 묻는다.
- `.env`, 키·토큰·자격 증명, `node_modules`, 빌드 산출물(`dist`) 등은 커밋 대상에서 제외하고, 포함돼 있으면 사용자에게 경고한다.

### 3. 커밋 메시지 작성

형식:

```
<type>: <한국어 요약>

<필요할 때만: 무엇을 왜 바꿨는지 본문>
```

| type | 용도 |
|------|------|
| feat | 사용자에게 보이는 새 기능·UI 추가 |
| fix | 버그 수정 |
| refactor | 동작 변경 없는 구조 개선 |
| chore | 설정, 의존성, 빌드, 문서 등 기타 |

규칙:

- 요약은 한국어로, 50자 안팎, 마침표 없이 쓴다.
- "무엇을 했는지"를 현재형 명사구나 평서형으로 쓴다. 예: `feat: 레트로 데스크톱 테마 적용`
- 본문은 요약만으로 부족할 때만 쓰고, "왜"를 중심으로 적는다.
- 기존 로그에 다른 관례가 확실히 있으면 그것을 따른다.
- 시스템이나 사용자 지침으로 요구되는 attribution 줄(예: Co-Authored-By)이 있으면 메시지 맨 끝에 붙인다.

### 4. 커밋 실행

승인을 기다리지 않고 바로 실행한다.

- 파일은 이름을 지정해 stage한다 (`git add <파일>`). `git add -A`와 `git add .`는 쓰지 않는다.
- 커밋 단위마다 `git commit -m` 으로 순서대로 커밋한다. 여러 줄 메시지는 heredoc을 사용한다.
- `--no-verify` 등 hook 우회 옵션은 쓰지 않는다. hook이 실패하면 원인을 알리고 고친 뒤 새 커밋으로 다시 시도한다.
- `--amend`, `push`, `reset` 같은 되돌리기 어렵거나 외부에 영향을 주는 작업은 사용자가 따로 요청할 때만 한다.
- 끝나면 `git log --oneline -n <커밋 수>`로 만들어진 커밋 목록과 메시지를 보여 준다.
