# TDD Rule

> **이 규칙은 Rigid — 상황에 맞게 변형하지 마라.** 단계를 건너뛰거나 순서를 바꾸지 않는다.

## 우선순위

- 프로젝트의 `CLAUDE.md` / `AGENTS.md`에 TDD 규칙이 있으면 **그 규칙이 우선**한다.
- 이 파일은 **기본값(fallback)** 이다. 프로젝트 규칙이 다루지 않는 부분에만 적용한다.

## 적용 기준

### 반드시 TDD를 적용한다

- 비즈니스 로직
- API (라우팅, 요청/응답 처리, 외부 호출 래퍼)
- 유틸 / 순수 함수
- **버그 수정** (버그를 재현하는 실패 테스트부터 작성)

### TDD가 불필요하다

- 타입 정의
- 설정 파일
- 순수 UI (로직 없는 마크업/스타일)
- SQL (스키마, 마이그레이션)

판단이 애매하면 **적용한다.**

## RED-GREEN-REFACTOR 사이클

### RED: 실패하는 테스트 작성

- **하나의 동작 = 하나의 테스트.** 한 테스트에 여러 동작을 섞지 않는다.
- 테스트를 **반드시 실행해서 실패를 확인**한다. 실행하지 않은 RED는 RED가 아니다.
- 실패 이유가 **"기능 미구현"** 이어야 한다. 오타, import 오류, 문법 오류, 환경 문제로 실패했다면 테스트를 고쳐 다시 RED를 만든다.

### GREEN: 최소한의 코드

- 테스트를 통과시키는 **최소한의 코드만** 작성한다.
- **YAGNI.** 아직 테스트가 요구하지 않는 분기, 옵션, 일반화는 추가하지 않는다.
- **신규 테스트와 기존 테스트가 모두 통과**하는지 실행해서 확인한다.

### REFACTOR: 정리

- 중복 제거, 이름 개선, 헬퍼 추출만 한다.
- 매 변경 후 테스트를 실행해 **green을 유지**한다.
- **새 동작을 추가하지 않는다.** 새 동작이 필요하면 다음 RED에서 시작한다.

### 반복

- 다음 동작에 대한 **RED로 돌아간다.** 요구사항의 모든 동작이 끝날 때까지 반복한다.

## 삭제 강제 규칙

- 테스트 전에 프로덕션 코드를 먼저 작성했다면 **그 코드를 삭제하고 RED부터 재시작**한다.
- **"참고용"으로 남기는 것도 금지.** 주석 처리, 별도 파일 보관, 기억해서 다시 쓰기 모두 해당한다.
- 테스트를 나중에 맞춰 쓴 경우도 동일하게 취급한다.

## 변명 차단표

| 변명 | 반론 |
|------|------|
| 너무 단순해서 테스트 불필요 | 단순한 코드는 테스트도 단순하다. 비용이 거의 없고, 이후 수정 시 회귀를 막는다. |
| 나중에 추가하겠다 | 사후 테스트는 구현을 그대로 추인할 뿐 설계를 이끌지 못한다. 실제로 추가되는 경우도 드물다. |
| 시간이 없다 | 디버깅과 회귀 수정이 테스트 작성보다 오래 걸린다. 급할수록 사이클을 지킨다. |
| 삭제하면 낭비다 | 이미 쓴 코드는 매몰 비용이다. 검증되지 않은 코드를 유지하는 쪽이 더 큰 비용이다. |
| 프로토타입이다 | 프로토타입은 프로덕션으로 넘어간다. 버릴 코드라면 버릴 때 같이 버리면 된다. |
